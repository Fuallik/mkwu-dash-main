# Uji backend nyata secara manual

Status 20 Oktober 2026: source backend lokal dibaca saja dan kini memuat metode pembayaran serta DELETE sesuai [kontrak](API-CONTRACT.md). Tidak menjalankan backend, memeriksa koneksi database, atau mengubah transaksi nyata pada task penyelesaian dashboard ini. Tes otomatis seluruhnya mock. Langkah integrasi di bawah untuk pengguna pada database dan order uji.

1. Pertahankan origin landing page backend. Tambahkan `http://127.0.0.1:5501`, dan `http://localhost:5501` bila dipakai, ke ALLOWED_ORIGINS sendiri. Pastikan ADMIN_SECRET backend acak kuat minimal 32 karakter. Jangan menyalin nilainya ke frontend, terminal command, catatan, screenshot, HAR, atau chat. Restart backend.
2. Dari `E:/cheesecake-api`, jalankan `.venv/Scripts/python.exe -m uvicorn main:app --reload --host 127.0.0.1 --port 8000 --no-access-log`. Dari terminal lain di `E:/cheesecake-dash/cheesecake-admin`, jalankan `python tools/serve.py --port 5501`. Landing page tetap pada port lain (misalnya 5500).
3. Buka `http://127.0.0.1:5501`. Sebelum login, workspace kosong dan tidak ada request admin. Password salah menghasilkan 401 dengan input dikosongkan. Password benar memanggil GET /admin/me lalu list dan summary; tidak ada POST login, Authorization, cookie, token atau storage. Jika memeriksa Network, jangan menyalin header secret/HAR. Preflight harus mengizinkan origin dashboard, X-Admin-Secret, Content-Type, GET/PATCH, tanpa credentials. Origin lain tidak memperoleh izin CORS.
4. Cocokkan list, search substring ID, empat filter, pagination 8/16/32, snapshot item, Rupiah/WIB, kontak dan summary dengan data uji. Summary tidak mengikuti filter; CANCELLED termasuk Nilai semua pesanan; hanya COMPLETED dihitung Sudah dibayar dan hanya PENDING dihitung menunggu. Dataset kosong harus empat nol. Simulasikan kegagalan summary non-autentikasi: statistik Tidak tersedia dan error tersendiri, sementara daftar sukses tetap tampil dan pagination/detail berfungsi. Uji summary lambat: daftar tersedia tanpa menunggu summary. Pulihkan summary dan muat ulang; error harus hilang. Summary 401/403 tetap mengunci dan membersihkan dashboard.
5. Pada order uji yang disetujui, ubah status menggunakan dropdown dan konfirmasi. Batal/Escape tidak mengirim PATCH. Uji PENDING/COMPLETED/CANCELLED dua arah, termasuk koreksi; order legacy NEEDS_REVIEW boleh dikoreksi ke ketiganya. payment_method null tetap dapat disimpan. Payload hanya status dan expected_status. Klik ganda menghasilkan satu PATCH. Sesudah sukses, detail/list/summary harus GET ulang; refresh halaman dan login lagi membuktikan persistensi.
6. Uji nomor null -> isi 08... -> edit +62.../628... -> kosongkan. Periksa normalisasi ke canonical, expected_wa_number persis dari detail, konfirmasi pengosongan, dan payload terpisah dari status. Input kosong, URL, huruf, ekstensi, Unicode digit atau >32 karakter harus ditolak; tidak ada link chat dari legacy/invalid/draft. Link valid hanya https://wa.me/digit canonical, tab baru tanpa opener/referrer. Nomor tidak muncul di list/publik/log. Nomor yang sama pada order uji lain tetap sah.
7. Pada order uji, periksa dropdown Metode pembayaran sesuai GET. Uji semua kombinasi null/QRIS/CASH termasuk no-op: label Belum ditentukan/QRIS/Tunai harus sesuai di daftar dan detail. Simpan metode pembayaran meminta konfirmasi; Batal/Escape tidak mengirim PATCH. Payload hanya `payment_method` dan `expected_payment_method`, keduanya wajib hadir termasuk null. Pilihan kosong mengirim JSON null. Klik ganda atau mencoba simpan status/kontak selama request hanya menghasilkan satu PATCH. Detail dan daftar dimuat ulang setelah sukses. Status, WA, item, harga, subtotal, diskon, total tidak berubah; QRIS tidak otomatis menjadi COMPLETED. Draft kontak tetap ada. Buat draft status/metode lalu simpan editor lain atau muat ulang: draft tersebut tidak ikut disimpan dan pemberitahuan muncul ketika dibuang.
8. Dua tab dengan snapshot sama: pada metode null, simpan QRIS di A lalu CASH di B. B harus 409 dan tidak menimpa A. Wajib GET detail berhasil sebelum simpan ulang; nilai expected berikutnya harus berasal dari GET baru. Target sama dengan nilai terbaru harus changed=false. Ulangi konflik untuk status dan kontak. Draft kontak tetap ada dengan pemberitahuan setelah GET; nomor tersimpan terbaru ditampilkan terpisah. Pengujian ini memerlukan dua sesi karena kredensial tidak disimpan setelah reload.
9. Pada lingkungan uji dengan intersepsi, tunda respons PATCH lebih dari 15 detik (termasuk simulasi commit sebelum timeout). Jangan kirim ulang otomatis. UI mengunci ketiga editor sampai GET detail berhasil; GET gagal tetap terkunci dan draft kontak dipertahankan. Uji juga PATCH sukses tetapi GET berikutnya gagal: simpan tetap tidak tersedia sampai GET berhasil. Uji 404, 409, 422, 429, 413, 503, HTML edge 200/5xx, koneksi putus dan error tanpa CORS. Pesan generik, tanpa retry loop/polling.
10. Logout atau respons 401 dari mutation pembayaran harus langsung mengosongkan tabel, statistik, detail, seluruh draft editor, kontak, konfirmasi, password dan credential. Reload/navigasi kembali juga terkunci. Request terlambat tidak boleh mengisi ulang data setelah logout. Password yang diketahui tetap berlaku sampai rotasi backend; tidak ada pencabutan sesi palsu.
11. Dengan server berheader/hosting uji, pastikan CSP mengizinkan gambar/CSS/module lokal dan origin API konkret, menolak script/koneksi tak terdaftar. Periksa no-store, nosniff, no-referrer, DENY dan frame-ancestors none. Verifikasi ulang sesudah mengganti API ke HTTPS publik. Catat tanggal, origin, order uji, hasil dan batas pengujian tanpa credential/kontak penuh.

12. Pada order uji PENDING/NEEDS_REVIEW/CANCELLED, buka detail dan klik **Hapus pesanan**. Pastikan dialog memperingatkan penghapusan permanen order dan rincian item. Input kosong, huruf kecil atau spasi tambahan pada Order ID tidak mengaktifkan konfirmasi; ID persis mengaktifkannya. Batal/Escape tidak mengirim DELETE. Detail COMPLETED tidak memiliki tombol hapus; mengubah draft dropdown saja tidak mengizinkan hapus.
13. Konfirmasi penghapusan order uji yang disetujui. Network harus menunjukkan satu DELETE `/admin/orders/{id}?expected_status=<status GET terakhir>`, tanpa body JSON. Klik ganda atau mencoba simpan editor lain selama proses tidak mengirim mutation tambahan. Respons 204 kosong diterima, detail ditutup, daftar/summary dimuat ulang. Uji juga satu-satunya order pada halaman terakhir dan satu-satunya order dalam hasil filter: pagination kembali valid dan empty state tampil bila perlu.
14. Ubah status melalui sesi uji lain sebelum konfirmasi hapus: respons 409 mengunci mutation sampai GET berhasil. Simulasikan timeout DELETE sebelum/sesudah commit: tidak ada retry DELETE; GET detail 404 membersihkan layar dan memperbarui daftar, sedangkan GET 200 menampilkan data terbaru. GET gagal tetap mengunci mutation. Logout/401 membersihkan Order ID konfirmasi dan seluruh data sensitif. Cascade nyata perlu diverifikasi terpisah pada database uji; hasil mock tidak membuktikannya.

Konfigurasi keamanan hosting belum diterapkan: lihat [security.md](security.md). Tes ini tidak dijalankan otomatis terhadap Supabase atau akun hosting.
